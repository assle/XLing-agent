# 高风险专业人工支持工作流

## 背景

原高风险流程用 LangGraph `interrupt()` 暂停图，以批准或拒绝决定是否恢复自动回复；等待期间拒绝用户继续留言，超时则把记录终结为 `escalated`。这种方式把专业支持缩减为一次模型审批，也无法表达接手、人工回复、站外联系、持续关注、转介和完成处置等实际工作。

需要让高风险消息进入可追踪的人工支持流程，同时保持每轮消息、安全评估、审核记录和后台任务的事务边界。该变更不恢复或迁移旧中断检查点。

## 决策

- 人工支持状态固定为 `pending → in_progress → monitoring / referred / completed`。高风险轮次保存安全评估和 `ReviewRequest`，发送固定确认后直接结束图执行，不再等待批准或拒绝，也不恢复 AI 回复。
- `pending` 与 `in_progress` 都允许用户继续留言。留言关联同一审核记录，保存用户消息和固定确认，不调用模型。
- 管理接口复用 `/api/admin/reviews/{id}`，提供 `claim`、`reply`、`contact` 和 `decision`。只有已接手记录可以回复、记录站外联系或作出处置；重复接手和已推进记录上的重复操作返回冲突。
- 人工回复使用 `SUPPORT` 角色，用户界面显示“支持人员”。回复与站外联系通过 `clientRequestId` 去重。
- 处置只接受 `monitor`、`refer`、`complete`。持续关注必须记录负责人和时间；转介必须记录去向、下一步和负责人；完成必须记录处理记录与完成依据。处置、用户说明和审计在同一事务提交。
- 超时只追加升级审计和 `ESCALATION_ALERT` 队列任务，不终结状态、不改变负责人、不写用户兜底消息。重复工作器不会重复创建同一审核的升级任务。
- 升级通知使用 `ESCALATION_ALERT_EMAIL_TO`，未配置时回退 `ALERT_EMAIL_TO`。真实支持人员、通知接收方、线下联系和转介能力仍由部署机构配置并验收，系统中的状态或通知不代表现实服务已完成。
- 旧 `approve` / `reject` 恢复入口、图中断和 `escalated` 终结状态退休。不读取旧中断继续执行，不执行旧数据迁移。

## 后果

高风险之后不再出现“批准后由模型继续回答”的路径。用户可以在人工接手前后补充情况，支持人员的回复、站外联系、处置和升级均保留审计依据。超时升级不会伪造人工处理结果，但部署方必须确保队列接收方和线下响应机制真实可用。

ADR-0003、ADR-0004 和 ADR-0005 中关于高风险中断、恢复与审核条件边的内容被本决策取代；其他检查点和条件边约定继续有效。ADR-0015 中“待审核会话拒绝新消息”的高风险限制同步废止。

## 验收

- 接口与界面测试覆盖接手权限、重复操作、人工回复和站外联系去重、三类处置必填信息、用户继续留言及 `SUPPORT` 标识。
- 事务测试覆盖用户补充消息成对保存或回滚，以及回复、站外联系、处置与审计的一致性。
- 超时测试覆盖非终结升级、队列任务幂等、无用户兜底消息及备用接收方配置。
- 浏览器界面覆盖 `pending` 只能接手、`in_progress` 可执行人工操作、终结状态只读。
