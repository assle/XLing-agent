# 人工支持的提交后实时事件流

## 背景

ADR-0018 已允许用户在 `pending` 和 `in_progress` 中继续留言，并允许当前负责人发送站内人工回复。消息和状态虽然已在同一事务中保存，用户端仍依赖定时轮询，后台人工队列依赖手动刷新，导致已保存的信息不能及时出现在另一端。

需要选择一种实时通知方式，同时保持现有发送接口、权限、幂等、固定安全确认、审计和不得恢复 AI 支持的约束。候选方案包括引入双向 WebSocket，或沿用现有 SSE 基础设施增加只读事件流。

## 决策

- 发送继续使用现有 HTTP POST 接口，实时接收使用两个受权限保护的 GET SSE 事件流：用户订阅自己会话的人工消息与状态，授权审核人员订阅人工支持队列。认证继续使用 Bearer 请求头，不把令牌放入 URL。
- 新增进程内人工支持事件模块，只在新需求、用户留言、人工消息或状态变化所属事务提交成功后发布。回滚不发布，幂等重试不重复发布，推送失败不改变已提交业务结果。
- MySQL 仍是消息和状态的最终依据，SSE 只是加速通知，不新增消息或事件表。连接与重连都先订阅并缓存事件，再读取 REST 快照，按消息编号和审核编号合并去重；队列溢出要求重新同步，不静默丢失。
- 前端使用带认证头的 `fetch` 读取 SSE，定期心跳防止代理超时。用户端在人工支持活跃时停止轮询；后台按审核编号局部更新并保留人工操作草稿，不再依靠整表刷新获得新内容。
- 当前事件总线只支持单应用进程。多 worker 或多主机部署必须另行选择跨进程分发或持久事件日志，不把本实现描述为分布式实时保证。

## 后果

用户补充留言和支持人员的站内回复可以在页面保持打开时及时到达，断线后通过数据库快照恢复完整状态。事件内容继续受会话归属和管理员权限约束，诊断边界与现实专业支持语义不变。

未采用 WebSocket 是因为当前发送接口已经完整，主要缺口是服务端到客户端的通知；复用现有 SSE 响应、Caddy 即时刷新和浏览器解析可以避免第二套发送协议。未来若要跨进程扩展，需要新的架构决议，而不是直接增加 worker 数量。

## 验收

- 服务端验证权限隔离、提交后发布、回滚不发布、幂等去重、人工回复和状态事件、SSE 断开清理。
- 浏览器验证用户人工消息实时追加、后台局部更新、快照与事件去重，以及实时更新时人工回复草稿和客户端请求编号不丢失。
- 端到端验证 `pending` 与 `in_progress` 用户留言无需后台刷新即可出现，人工回复无需用户轮询即可出现，重连后无遗漏或重复。
